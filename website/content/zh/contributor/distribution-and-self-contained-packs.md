# 为什么我们选择自包含包

开箱即用的便利，需要有人持续协调实现与环境；把算法留在各自的边界内，则要承担逐包声明和校验的工作。HoloLab 优先选择抗腐坏与可复现，采用自包含 pack。我们愿意为以后或另一台机器上仍能重建管线，放弃统一集成带来的零配置便利。

## 现实做法是这次取舍的依据

以下不是 HoloLab 提供的可选菜单，而是我们权衡过的现实做法。它们分别回答谁维护实现、谁解决依赖、谁承担升级影响；把代码放进一个目录，并没有回答这些问题。

| 分发形态 | 怎么接入 | 好处 | 代价 |
| --- | --- | --- | --- |
| 各家官方仓库，直接 clone | 算法留在自己的仓库、自己的环境，平台包一层入口与接口 | 与上游一致 | 每个算法一套环境，入口与接口各不相同，包装工作逐个完成 |
| 统一抽象层，diffusers 式 | 各模型实现同一套 pipeline 接口，复用同一底座 | 接口统一 | 每个模型都要适配抽象；依赖的 `>=x,<y` 版本区间容易互相冲突 |
| 中心化大集成，ComfyUI 式 | 各模型实现在核心仓内重写并集中维护，共享一套极薄依赖 | 零配置、开箱即用 | 主干膨胀，实现与上游脱节，持续依靠社区 PR 补入新模型 |

中心化的“零配置”指能力集成：不必逐个拼装官方仓库和插件。运行环境仍需安装，模型权重仍需取得。统一接口也不会自动统一模型内部结构；适配工作只是换了位置。

## ComfyUI 的便利由集成方持续承担

以下数字来自已检查的 ComfyUI 实例，只描述该次检查的状态。

| 检查项 | 实测结果 | 说明 |
| --- | --- | --- |
| `comfy/ldm/` | 52 个模型族的原生实现 | 推理代码随仓库分发，clone 即有 |
| `models/` | 只有 5 个自行下载的文件 | 有实现不等于有权重，权重需自行下载 |
| `requirements.txt` | 仅 36 行，无 diffusers | 核心代码也无 `import diffusers`；`diffusers_convert.py` 用于权重格式转换 |
| `custom_nodes/` 与 `comfy_extras/` | 前者为空，后者有 152 个内置节点文件 | 开箱能力来自内置节点，第三方插件不是运行前提 |

这些原生实现不只覆盖生成模型。SAM3 做分割，RT-DETR 做检测，MoGe 做几何，Depth-Anything-3 做深度，Hunyuan3D / TripoSplat 覆盖 3D 与高斯重建。

这不是把 diffusers 包装成节点。各模型族结构各异，每个都要单独适配，实现由集成侧自行重写。模型实现主要由社区 PR 贡献。例如 MiniMax-H3 的提交历史署名为社区开发者 kijai，经 PR 合入，并非模型方或官方团队直接提供。

**依赖压平是一份环境装下 52 族的前提。** 避开各官方仓库的环境，也避开 diffusers 的依赖体系，再由项目自行发布关键包并精确钉住版本，例如 `comfy-kitchen==…`、`comfyui-frontend-package==…`。使用者少做的环境协调，转成了集成方持续承担的重写、适配与维护。

Partner/API Nodes 是另一条线：厂商合作通过云端 API 提供能力。它们不属于上述本地原生实现，不能混为同一种分发方式。

## HoloLab 选择自包含包与环境契约

我们的选择是**自包含 pack ＋ 环境契约 ＋ 包身份**，由注册表承接包的查找与分发。算法实现分散维护，身份可以集中解析；注册表不因此变成模型实现的大仓库。

**抗腐坏与可复现，比第一次运行时少做配置更重要。** 工作流要能交给别人，也要能留给以后的自己；今天能跑，不能替代以后能解释并重建。一个算法升级环境，不应牵动其他算法。为此，我们接受逐包维护执行契约的工作，不把统一环境的便利作为首要目标。

固定代码来源与依赖身份，声明执行条件，才能在以后或另一台机器上重建管线。[包身份与注册表](/docs/contributor/package-identity-registry)负责回答“是哪份包”，[工作流重建](/docs/contributor/rebuild-and-distribute)负责划分配方与本地状态。这里的可复现指管线可重建，不承诺数值或产物完全一致。

## 我们承担包边界上的成本

选择自包含包，没有消除集成工作。下表说明这次取舍把责任放在哪里，也说明我们接受了哪些成本。

| 形态 | 代码归属 | 环境 | 新算法怎么进来 | 主要代价 |
| --- | --- | --- | --- | --- |
| 中心化大集成 | 实现进入核心仓，由集成方与社区维护 | 共享依赖，集中协调版本 | 重写、适配，经 PR 合入主干 | 主干膨胀、上游差异累积，共享环境的升级影响多个模型 |
| 自包含 pack | 算法留在自己的仓，包声明来源与执行契约 | 每包声明并校验环境，升级影响限制在包边界内 | 提供入口、类型化接口、环境声明与可追溯身份 | 环境碎片化，每包自证依赖，跨环境传数据需要明确约定 |

自包含不要求把所有源码和依赖复制进包。它要求执行所需的代码来源、依赖条件、接口与失败条件都能从包的声明中得到解释，不靠作者机器上的隐含状态。

这条路保留了环境碎片化的成本。包作者要证明依赖足够，使用者可能需要维护不同环境。跨环境交接也必须约定数据类型、序列化格式与文件可达性；某个进程里的对象或某台机器上的路径，不能直接当作另一环境已经可用的输入。

## 把这次取舍落实到每个 pack

以下五条规则，是优先保证抗腐坏与可复现这一选择在日常工作中的落点。包作者把执行条件写清并接受校验，才能让后续使用者不必猜测作者机器上的状态。

1. **实现留在算法自己的仓。** 平台只声明 `source_entry` 与接口，不把算法实现搬进平台。入口负责接通执行，不能隐藏代码来源。
2. **依赖写进 manifest 的环境声明。** 声明运行时、库与硬件要求；运行前按声明校验。不满足就明确失败，不静默降级到另一套实现或环境。
3. **包自己解释输入、输出与失败条件。** 写清类型、数据约定和拒绝执行的条件，不依赖“平台会替我兜底”。跨环境传递的数据同样属于接口契约。
4. **保留与上游的可追溯关系。** 外部依赖记录 commit 或版本，不能只指向“某个时间点的目录”。包身份要能追到实际执行的代码。
5. **依附大包时声明外部运行时依赖。** 若算法只能通过别人的大包运行，例如 H3 经 ComfyUI 执行，就明确记录 ComfyUI 是外部运行时依赖。说明所依赖的版本与状态，以及共享进程、依赖或配置变化可能带来的状态耦合风险。包装成 pack 不会自动解除这种耦合。

**能力要能被表达成“类型化的输入输出 + 可复现的执行”，否则先不要接。**
