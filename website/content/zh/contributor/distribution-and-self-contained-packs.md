# 以算法组件为分发单位

**我们不希望一个研究算法为了成为管线的一部分，就必须迁就整条管线的运行环境。** HoloLab 选择自包含 pack，是为了降低算法接入不同实验时的适配成本。算法保留自己的代码、依赖和运行方式，通过尽量薄的接口暴露能力，作为独立组件被复用和分发。

## 抽象单位决定优化对象

ComfyUI 面向创作者组合现有能力，在创作工作流的组合与交付上已经成熟，并持续演进。HoloLab 面向研究算法的快速接入与调度，关注一个算法怎样进入多条实验管线。这里比较的是目标用户与抽象单位，不评价谁在同一件事上做得更强。

| 关注点 | ComfyUI 的工作流交付 | HoloLab 的算法分发 |
| --- | --- | --- |
| 打包单位 | 单个工作流及其运行环境，见 Comfy API Builds | 算法组件本身 |
| 服务目标 | 一份作品的工作流能交付、能运行 | 一个算法能跨管线复用、能独立发布 |
| 固定的边界 | 工作流需要的节点、模型与依赖 | 算法的代码来源、执行条件与接口 |

**作品级可复现与算法级可复用是两种目标。** 前者需要固定一份工作流及其环境，后者需要让算法包跨多条管线使用并独立升级。两者各需自己的机制，也可以同时存在。

## ComfyUI 已有工作流部署机制

截至 2026-10-01，[Comfy API Builds 已正式上线](https://blog.comfy.org/p/comfy-api-is-live-deploy-comfyui)：把工作流连同自定义节点、模型与 Python 依赖打包为 Build，再切出不可变 release，部署为托管端点，也可自托管。官方明确说明 Builder 会帮助解决 Python 依赖冲突。这里的交付粒度是工作流及其所需环境，不是把整个实例作为抽象单位，也不是把其中每个算法分别发布为独立组件。

[comfy-cli](https://github.com/Comfy-Org/comfy-cli) 也提供 `install-deps`、`save-snapshot`、`restore-snapshot` 等依赖与环境管理命令。[2025 年公布的 Nodes v3 方案](https://blog.comfy.org/p/dependency-resolution-and-custom)还提出了自定义节点包的进程隔离；这一项仍是待完善的提案，尚未落地。HoloLab 的选择不以 ComfyUI 缺少可复现部署或依赖管理能力为前提，而以算法组件需要独立复用为出发点。

## 中心化集成供给开箱能力

以下数字来自已检查的 ComfyUI 实例，只描述该次检查的状态。它们说明集成方如何供给实现与运行环境，让创作者直接组合已有能力。

| 检查项 | 实测结果 | 说明 |
| --- | --- | --- |
| `comfy/ldm/` | 52 个模型族的原生实现 | 推理代码随仓库分发，clone 即有 |
| `models/` | 只有 5 个自行下载的文件 | 有实现不等于有权重，权重需自行下载 |
| `requirements.txt` | 仅 36 行，无 diffusers | 核心代码也无 `import diffusers`；`diffusers_convert.py` 用于权重格式转换 |
| `custom_nodes/` 与 `comfy_extras/` | 前者为空，后者有 152 个内置节点文件 | 开箱能力来自内置节点，第三方插件不是运行前提 |

这些原生实现不只覆盖生成模型：SAM3 做分割，RT-DETR 做检测，MoGe 做几何，Depth-Anything-3 做深度，Hunyuan3D / TripoSplat 覆盖 3D 与高斯重建。ComfyUI 因此不只是一层 diffusers 薄壳，而是提供经过适配的模型实现及配套依赖。MiniMax-H3 的提交历史署名为社区开发者 kijai，经 PR 合入；这一实现的来源不能直接归为模型方或官方团队。

关键包如 `comfy-kitchen`、`comfyui-frontend-package` 由项目发布并精确钉住版本，体现了集中协调实现与环境的方式。使用者由此不必逐个拼装官方仓库，但仍需安装运行环境、取得权重。这些观察描述的是开箱集成的形态，不是选择自包含包的反面证据。

Partner/API Nodes 是另一条线：厂商合作通过云端 API 提供能力。它们不属于上述本地原生实现，不能混为同一种分发方式。

## 算法包保留自己的执行边界

HoloLab 采用**自包含 pack ＋ 环境契约 ＋ 包身份**，由注册表承接查找与分发。算法实现分散维护，身份集中解析；管线通过接口调度算法，不要求每个算法改写到同一套运行环境中。

例如，同一个重建算法包可以接入不同的数据准备与评估管线，而不为每条管线重新移植实现。算法可独立发布新版本，各管线明确选择所引用的版本。薄接口仍须说明输入、输出与执行条件；保留运行方式不等于免除适配责任。

自包含不要求把所有源码和依赖复制进包，而要求包能解释代码来源、依赖条件、接口与失败条件。[包身份与注册表](/docs/contributor/package-identity-registry)回答“是哪份包”，[工作流重建](/docs/contributor/rebuild-and-distribute)划分配方与本地状态。这些机制支持独立组件的组合与管线重建，不承诺数值或产物完全一致。

## 自包含包的代价

算法保留自己的环境，就需要承担包边界上的集成工作。我们减少的是算法迁就整条管线环境的成本，同时接受以下责任。

| 代价 | 需要承担的工作 |
| --- | --- |
| 环境碎片化 | 使用者可能需要维护多套运行环境 |
| 每包自证依赖 | 作者声明并验证依赖足够，不能依靠作者机器上的隐含状态 |
| 跨环境传数据 | 双方约定数据类型、序列化格式与文件可达性 |

某个进程里的对象或某台机器上的路径，不能直接当作另一环境已经可用的输入。独立升级也需要兼容的接口和明确的版本引用；包装成 pack 本身不会自动隔离共享运行时的状态。

## 把选择落实到每个 pack

以下五条规则，是以算法组件为分发单位这一选择在日常工作中的样子。作者把边界写清并接受校验，算法才能被不同管线可靠地接入。

1. **实现留在算法自己的仓。** 平台只声明 `source_entry` 与接口，不把算法实现搬进平台。入口负责接通执行，不能隐藏代码来源。
2. **依赖写进 manifest 的环境声明。** 声明运行时、库与硬件要求；运行前按声明校验。不满足就明确失败，不静默降级到另一套实现或环境。
3. **包自己解释输入、输出与失败条件。** 写清类型、数据约定和拒绝执行的条件，不依赖“平台会替我兜底”。跨环境传递的数据同样属于接口契约。
4. **保留与上游的可追溯关系。** 外部依赖记录 commit 或版本，不能只指向“某个时间点的目录”。包身份要能追到实际执行的代码。
5. **依附大包时声明外部运行时依赖。** 若算法只能通过别人的大包运行，例如 H3 经 ComfyUI 执行，就明确记录 ComfyUI 是外部运行时依赖。说明所依赖的版本与状态，以及共享进程、依赖或配置变化可能带来的状态耦合风险。包装成 pack 不会自动解除这种耦合。

**能力要能被表达成“类型化的输入输出 + 可复现的执行”，否则先不要接。**
