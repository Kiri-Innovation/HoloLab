# 用变量、本地绑定与快照保留执行语义

> **开发中**：本节描述的能力尚在开发中，完成后此标记会移除。

两个人运行同一条重建管线，可以使用不同的数据目录和设备，但仍共享同一份拓扑与参数定义。变量把这些本地选择从配方里分离出来；快照则回答某一次运行实际使用了什么。

## 参数保留内联值，也可以绑定变量

工作流变量的**名称、类型、说明、默认值**随配方分发；变量值保存在本地绑定中。默认值属于共享声明，不把原作者的本地取值变成接收者的绑定。

变量类型只包含标量：`path`、`int`、`float`、`bool`、`string`、`enum`。变量不绑定 arrayed 或端口类型，避免与 fan-out 的数组展开语义冲突。

参数有两种输入状态：

| 状态 | 编辑与解析语义 |
| --- | --- |
| 内联值 | 直接在参数位置给值，保留原地编辑的内联感 |
| 绑定工作流全局变量 | 从下拉框选择变量；列表按类型过滤，只允许选择类型匹配的变量 |

例如，多个参数绑定同一个迭代次数变量时，修改该变量会同时改变所有绑定它的参数。**变量值变化必须触发相关下游产物的陈旧传播**，否则下游仍显示绿色，会让用户误认为旧产物对应新值。

快照冻结的是**解析后的参数值**，不论值来自内联输入还是变量。一次运行解析到 `12000`，之后变量改成 `10000`，旧快照仍回答“那次用了 `12000`”，不能依靠现在的变量值反推过去。

## 环境要求共享，设备选择留在本地

包 manifest 声明节点需要的 GPU、24GB 显存或某个运行环境；这些是可分发的能力要求。具体选择哪台机器是本地绑定，`assigned_node_id` 这样的机器 UUID 不随配方共享。

别人打开你的 workflow，节点全部处于**未分配**状态。这是正确的起点，而不是丢失数据：界面清晰标示未分配，并提示哪些机器能满足该节点的要求。路径变量也由接收者绑定到自己的环境，不能沿用原作者的绝对路径来假定数据存在。

## 快照记录一次运行的重建依据

一个快照由以下内容组成：**配方引用 + 本地绑定 + 依赖清单 + 可选环境指纹 + 可选输入数据摘要**。

| 内容 | 回答的问题 |
| --- | --- |
| 配方引用 | 使用哪一版 workflow？ |
| 本地绑定 | 使用哪些机器、哪些变量值？参数解析后的值是什么？ |
| 依赖清单 | 每个包的名字、版本、哈希是什么？ |
| 环境指纹（可选） | 当次执行环境的身份是什么？ |
| 输入数据摘要（可选） | 当次输入数据的身份是什么？ |

快照是重建一次运行的依据；记录充分时，别人能据此重建管线，缺少依据时，它只是一台机器上的备忘录。这里不把两项可选记录变成必填条件，也不把它们的存在当作结果完全一致的保证。环境指纹与输入摘要帮助核对当时的条件；随机种子、硬件与库版本以及算法内部非确定性仍影响结果。

快照中的原机器和原变量值保留历史事实，不代表它们能直接成为另一台机器上的有效绑定。共享配方与包后，接收者按记录重建，并在自己的环境中完成绑定；运行记录本身仍属于本地状态。

当前实现只具备部分配方和部分绑定记录，缺少哈希、环境与输入数据身份。这些缺口解释了为什么仅保留一份图还不足以说明当时运行的完整条件。

## 发版怎样连接已有快照

假设一次 run 使用开发包 `name@0.1.1+`，快照记录哈希 `H`。随后当前算法发布为 `0.1.1`，其哈希同样是 `H`。

**已完成的快照不改写。** 它保留原身份 `0.1.1+ @H`，另加前向指针 `published_as: 0.1.1`。于是系统可以判定“这个快照的依赖可通过 `0.1.1` 满足”，而不是声称“当时跑的就是 `0.1.1`”。快照是当时发生了什么的证据，不能通过覆盖原身份改变历史。

发版时，系统扫描同名包的 `name@X+` 历史快照，并对哈希相等的记录批量加注。仅版本名称相近不成立，哈希必须相同。

**仍在运行中的 run（in-flight）是例外，可以直接重指**到对应的发布版本。它还不是已完成的历史，而是正在发生的执行；此例外不放宽已经完成的快照不可改写的规则。

## 用 git 协作，避免共享个人视图

workflow 是文件，因此直接复用 git 的分支、合并、冲突解决与历史追溯模型。协作者共享配方，不共享机器绑定和变量值，不需要另造一套工作流协作机制。

画布坐标 `position` 是已知的协作噪音源：每次拖动都会制造 diff。个人视图状态与配方语义分开处理；布局采用本地叠加，或在同文件中分节并在冲突时本地优先。这两种组织方式都让个人排布不覆盖共享的管线意图；`preview_open` 同样属于个人视图状态。
