# 让工作流在另一台机器上重建

> **开发中**：本节描述的能力尚在开发中，完成后此标记会移除。

把一条跑通的工作流交给同事，对方需要知道如何组装和运行它，而不是接管原作者的机器。系统以此划分可分发内容与本地状态：workflow 像代码一样可分发，算法包像 pip 包一样可同步、可分发。钉住版本是实现这个目标的手段，不是目标本身。

## 共享重建方法，明确保证的边界

分发的是**配方，不是产物**。接收者拿到“怎么重建”，产物由接收者运行得到。这里的“可复现”有两个不同强度，不能互相替代。

| 强度 | 含义 | 系统保证 |
| --- | --- | --- |
| 管线可重建 | 拿到配方和包，能组装出同样拓扑、同样参数、同样版本的管线并运行 | 保证 |
| 结果可复现 | 跑出的数值或产物一模一样 | 不保证 |

结果完全一致还取决于随机种子、硬件与库版本，以及算法内部的非确定性，例如多线程归约和 cuDNN 的算法选择。管线重建的保证不等于这些条件已经相同，也不等于消除了非确定性。

Gateway 因而承担**解析器与执行器**的职责，而不是数据的主人。用户持有的 workflow 文件与包生态才是可分发的资产；换一个 Gateway 不改变配方的身份。

## 按五层决定什么随工作流分发

| 层 | 内容 | 载体 | 是否分发 |
| --- | --- | --- | --- |
| 配方 Recipe | 拓扑、参数、pin 配置、变量声明与默认值 | workflow 文件 | 是 |
| 依赖 Dependency | 算法包 `scope/name@version` 与哈希 | 包生态、注册表 | 是 |
| 环境 Environment | Python、conda、CUDA 等运行时依赖；显存、GPU 架构等硬件要求 | 包 manifest 声明 | 是 |
| 本地绑定 Binding | 每个节点选用的设备、变量值 | 本地 SQLite | 否，不能随配方分发 |
| 运行记录 Record | runs、jobs、snapshots、事件、日志 | 本地 SQLite | 否，无需随配方分发 |

变量的声明与默认值是配方的一部分，某次本地使用的变量值则属于绑定。环境层表达“需要什么”，绑定层表达“在这里具体选什么”。同样，运行记录保留执行证据，不成为共享配方的一部分。

判断一个字段归属时，先问：**换一台机器、换一个执行端，这东西应该是同一个，还是应该重新产生？** 应该相同的内容归入配方；应在新环境重新产生的内容归入本地状态。包身份与环境要求分别通过依赖层和 manifest 保持可分发。

## 为什么不能直接把现有 JSON 放进 git

> **过渡章节**：本节描述拆分之前的实现，只用来说明拆分的动机。拆分落地后，本节连同标题一并删除。

当前实现把整个 workflow 存为一个 `draft_json` JSON blob。它把不同性质的内容放在了一起：

| 字段 | 性质 |
| --- | --- |
| `nodes`、`edges`、`params`、`algorithm_name`、`algorithm_version` | 配方；其中参数里的机器相关值需要单独识别 |
| `assigned_node_id` | 本地设备绑定，值是机器 UUID |
| `params.video_dir` 中的 `/cloud/...` 绝对路径 | 环境相关的本地绑定，通过变量表达 |
| `position`、`preview_open` | 个人视图状态 |

直接提交这个 blob，并不能让工作流跨机器成立：`assigned_node_id` 指向接收者没有的设备，`video_dir` 指向接收者没有的路径。问题不在于 JSON 能否进 git，而在于共享内容的边界。

拆分后的配方保留拓扑和参数意图；机器与路径等本地选择由接收者重新绑定。[变量、本地绑定与快照](/docs/contributor/variables-bindings-snapshots)说明参数如何引用变量，以及运行时怎样冻结实际值。

## 用包身份连接配方与执行

配方通过精确的包身份引用算法。发布版本不可变，开发版本的实际代码通过快照中的哈希留证；源地址由本地配置决定。[包身份与注册表](/docs/contributor/package-identity-registry)定义这些规则。

**核心不变量：当 workflow 引用的所有包都不带 `+`（即都有确定哈希）时，该管线可复现。** 这里“可复现”严格指**管线可重建**：在取得配方和依赖包、满足声明的环境要求并完成本地绑定后，能够按同样拓扑、参数与版本运行；它不承诺产物或数值一模一样。
